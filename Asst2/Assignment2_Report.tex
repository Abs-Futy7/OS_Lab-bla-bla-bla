\section{Code Evidence and Explanation}

\subsection{System Call Interface}

\shot{screenshots/syscall-prototypes.png}{Syscall Prototypes}{This screenshot shows the new kernel function declarations in \texttt{kern/include/syscall.h}. Functions such as \texttt{sys\_fork}, \texttt{sys\_waitpid}, \texttt{sys\_open}, \texttt{sys\_read}, and \texttt{sys\_write} are declared here so the syscall dispatcher can call their implementations. This file acts like the common interface between the low-level trap handler and the syscall source files.}

\shot{screenshots/syscall-dispatcher.png}{Syscall Dispatcher}{The dispatcher reads the syscall number from the trapframe and uses a \texttt{switch} statement to call the correct kernel function. For example, \texttt{SYS\_open} calls \texttt{sys\_open}, \texttt{SYS\_fork} calls \texttt{sys\_fork}, and return values are placed back into the trapframe registers. This is the main entry point for user programs requesting kernel services.}

\subsection{Synchronization}

\shot{screenshots/lock_create.png}{Lock Create}{\texttt{lock\_create} allocates memory for a lock, copies the lock name, creates the wait channel, initializes the internal spinlock, and sets the initial owner state to free. The wait channel is used when a thread must sleep, while the spinlock protects the lock's internal fields.}

\shot{screenshots/lock_acquire+release.png}{Lock Acquire and Release}{\texttt{lock\_acquire} first protects the lock state using the internal spinlock. If the lock is already held, the current thread sleeps on the wait channel until it is woken. \texttt{lock\_release} clears the holder, marks the lock free, and wakes one sleeping thread so another thread can enter the critical section.}

\shot{screenshots/cv_wait+signal+broadcast.png}{Condition Variables}{\texttt{cv\_wait} is used when a thread cannot continue until some condition becomes true. It releases the caller's lock before sleeping and reacquires it after wakeup, preventing deadlock. \texttt{cv\_signal} wakes one waiting thread, and \texttt{cv\_broadcast} wakes all threads waiting on the condition variable.}

\subsection{Process System Calls}

\shot{screenshots/sys-gerpid+waitpid.png}{getpid and waitpid}{\texttt{sys\_getpid} simply returns the PID stored in the current process structure. \texttt{sys\_waitpid} validates that the requested PID belongs to a child process, sleeps until that child exits, then returns the encoded exit status to the parent through the user pointer. This gives the parent a controlled way to collect child termination information.}

\shot{screenshots/sys-fork.png}{fork}{\texttt{sys\_fork} creates a new process by copying the parent's trapframe and address space. It also copies references to open file handles so the child inherits the parent's open files. After \texttt{thread\_fork}, the parent returns the child PID, while the child enters user mode with return value 0.}

\shot{screenshots/run-program_args.png}{runprogram Arguments}{\texttt{runprogram\_args} loads the executable, creates the user address space, and copies argument strings onto the new user stack. It then builds the \texttt{argv} pointer array and passes \texttt{argc} and \texttt{argv} to \texttt{enter\_new\_process}. This is why menu commands with extra words can be received by user programs.}

\subsection{File System Calls}

\shot{screenshots/filehandle.png}{File Handle}{The file handle structure stores the vnode, current offset, open flags, reference count, and a lock. The vnode points to the actual file object in the VFS layer. The offset tracks where the next read/write happens, and the refcount allows parent and child processes to safely share the same open file after \texttt{fork}.}

\shot{screenshots/filehandle2.png}{Process File Table}{Each process owns a file descriptor table named \texttt{p\_filetable[OPEN\_MAX]}. A user file descriptor is just an integer index into this table. When a file is opened, the kernel finds a free slot, stores the file handle there, and returns the slot number to the user program.}

\shot{screenshots/sys-open.png}{open and create}{\texttt{sys\_open} copies the filename from user memory using safe copy functions, checks the open flags, and calls \texttt{vfs\_open}. After a vnode is returned, it creates a file handle and stores it in the process file table. \texttt{O\_CREAT} is handled through the VFS open flags so a missing file can be created.}

\shot{screenshots/sys-read+write.png}{read, write, and append}{\texttt{sys\_read} and \texttt{sys\_write} use \texttt{uio} and \texttt{iovec} objects because OS/161 file I/O must safely transfer bytes between user memory and the kernel/VFS layer. The file handle lock protects the offset while I/O is happening. For \texttt{O\_APPEND}, \texttt{sys\_write} first moves the offset to the file size, then writes at the end.}

\shot{screenshots/sys-close+remove.png}{close and remove}{\texttt{sys\_close} clears the descriptor entry in the process file table and decreases the file handle reference count. When no process uses the handle anymore, the vnode is closed and memory is freed. \texttt{sys\_remove} copies the pathname from user space and calls \texttt{vfs\_remove} to delete the file from the mounted filesystem.}

\section{Short Viva Notes}

\begin{itemize}
  \item \texttt{fork}: parent gets child PID, child gets 0.
  \item \texttt{waitpid}: only parent can wait for child status.
  \item \texttt{execv}: replaces address space but keeps same PID.
  \item File descriptors point to refcounted file handles.
  \item Parent and child share file handles after \texttt{fork}, so offsets are shared.
  \item \texttt{O\_APPEND}: write first sets offset to current file size.
  \item Argument passing: strings and \texttt{argv[]} are copied to the new user stack.
\end{itemize}
